## 1. 目标与阶段边界

将当前实验 NAS 控制完善为日常使用通路：

1. ESP32 保留蓝牙、WiFi 配网、WiFi 联网和 MQTT，移除设备 HTTPS 服务。
2. 设备本地 PIR、自动排风、定时和安全保护独立运行，不依赖 App、NAS 或互联网。
3. MQTT 承担设备状态上报、控制和必要的数据查询。
4. NAS 缓存实时状态，持久归档历史数据，对 App 提供经过认证的 HTTPS API。
5. App 前台定时读取 NAS 缓存；进入前台或网络恢复时立即获取完整快照。
6. NAS 不可用时明确提示，可切换蓝牙；不再回退设备 HTTPS。

本阶段范围外的能力及边界见 §1.1；未来扩展保留版本和能力字段，不预先实现这些服务。

### 1.1 明确不做的范围

- App 后台保活、厂商通知通道及后台实时推送。
- 公网访问、路由器端口转发、云端 Broker 和自动云端切换。
- 独立多用户账号体系、角色分级、家庭成员邀请；现有最多三手机绑定、设备权限校验和 NAS 只读授权仍需实现，不能借此排除。
- NAS 回写或恢复设备全部历史、修改设备已产生的原始归档。
- 米家接入、设备侧 WebSocket、设备 HTTPS 恢复及 MQTT 固件包传输。
- 本阶段 App 与 NAS 的 WebSocket/SSE；前台只实现有界轮询。

上述能力需要另立需求和验收，不能以“顺手补齐”并入本轮。

“移除 HTTPS”仅指 ESP32 上的 HTTPS 服务。NAS 上供 App 使用的 HTTPS 必须保留。BLE OTA 继续使用已有的签名、断点续传和安装确认流程。

## 3. 总体结构与职责

```text
App ──认证 HTTPS──> NAS Gateway ──MQTT──> ESP32
 │                       │                │
 │                       ├─实时状态缓存   ├─本地风机/PIR 状态机
 │                       └─历史数据库     ├─持久化控制去重
 └──────── BLE ──────────────────────────└─配网、维护、备用控制、OTA
```

| 组件 | 职责 |
| --- | --- |
| ESP32 | 本地业务、权限校验、执行控制、产生原始状态和统计、维护有限历史 |
| Mosquitto | 消息传递、认证、Topic ACL、会话和遗嘱；不负责业务授权 |
| Gateway | 认证 App、关联请求、转换协议、缓存状态、同步历史、提供诊断 |
| NAS 数据库 | 保存历史、覆盖范围、同步游标与必要的网关元数据 |
| App | 选择通道、显示状态和新鲜度、保存待确认请求、前台刷新、蓝牙维护 |

Broker 接受消息不等于设备接受控制；设备返回执行成功不等于风机此刻仍在运行。请求结果与当前设备状态必须分开保存和展示。

## 4. 固件模块拆分及 HTTPS 移除

### 4.1 先拆分，后删除

`WifiHttpsServer.cpp` 当前承载 MQTT 也在使用的逻辑，不得整文件直接删除。目标模块名可按项目规范调整，但职责必须分离：

| 原有职责 | 目标归属 | 要求 |
| --- | --- | --- |
| 命令互斥、租约、请求查询、去重与恢复 | ControlCommandService | MQTT/BLE 共享执行约束，初始化不依赖网络服务 |
| 参数及业务规则 | 现有 ControlApi、FanController | 保留原有安全规则，避免传输层另写业务逻辑 |
| 快照、状态版本、采样 | DeviceStateService | 统一供 MQTT 和 BLE 读取 |
| 绑定更新和撤销 | WifiBindingStore | 由独立生命周期调用，不藏在 HTTPS 更新函数内 |
| MQTT 连接、组包、发送和接收 | WifiMqttTransport | 不持有风机业务的另一份状态 |
| HTTP 路由、TLS 服务和连接回收 | 设备 HTTPS 专属模块 | 共用逻辑验证后移除 |

BLE 不必照搬 MQTT 两阶段消息格式；应复用参数校验、业务锁、冲突规则和明确的执行结果。有请求 ID 的 BLE 写控制应走同一去重服务；兼容旧 BLE 控制时，必须声明其不支持跨通道自动重发。

### 4.2 初始化与并发

- 命令锁、存储恢复和绑定服务在网络通道启动前初始化。
- 去重恢复未完成时禁止写控制，返回明确的暂不可用原因；不能覆盖尚未恢复的记录。
- 状态快照保持有界内存占用。MQTT 事件回调不得直接无限等待主循环业务。
- 控制和查询采用有界调度；大统计查询分页处理，不能长时间占住业务锁。
- PIR 检测、风机状态机和安全时限的调度优先于历史同步。
- MQTT 重连不重复创建客户端，不泄漏任务、队列或连接；创建失败也要退避。

### 4.3 删除清单

移除设备 HTTP/TLS server、HTTP 路由注册、空闲连接回收、仅服务于 HTTPS 的快照拼装、设备直连探测和 App 设备 HTTPS 回退代码。同步清理仅为服务端握手引入的构建补丁及测试。

不要按文件名批量删除密码学代码。设备 ID、绑定凭据、MQTT 控制校验、随机数、OTA 验签仍需保留。HTTPS 服务证书、云端 MQTT 的 CA 信任和设备身份是不同用途，分别检查引用后决定去留；未来 MQTT TLS 不要求沿用当前设备自签服务证书。

## 5. 协议版本与能力声明

### 5.1 版本分层

| 协议 | 本阶段约定 |
| --- | --- |
| App 到 NAS API | 保留 `/api/v1`；不兼容变更必须另起版本 |
| MQTT 控制及 ACK | 沿用 `version: 2`、prepare/execute 两阶段 |
| MQTT 状态、能力、只读查询 | 新增独立 `schemaVersion: 1` |
| 统计存储 schema | 与传输协议独立；不因新增字段随意修改存储 schema |
| MQTT Topic 中的 v1 | Topic 命名空间版本，不等同消息 version |

缺少新状态能力的旧设备只能进入显式的兼容模式，不能被标记为完整支持新鲜度和增量历史。

### 5.2 能力消息

连接并完成所需订阅后发布设备能力，能力变化或固件升级后重新发布：

```json
{
  "schemaVersion": 1,
  "deviceId": "32位设备ID",
  "firmware": "实际固件版本",
  "controlVersions": [2],
  "stateVersions": [1],
  "features": ["state-seq", "read-query-v1", "stats-cursor-v1", "ble-ota", "time-sync-v1"],
  "maxPayloadBytes": 1024
}
```

以上是结构示例，features 只能声明已经实现并验证的能力。Gateway 校验版本和必需能力后开放对应功能；未知的可选字段可忽略，不支持的关键版本必须明确拒绝。

本轮不引入复杂的多轮协商。能力消息不能阻塞设备本地自动运行，也不能代替设备端授权。

### 5.3 三种字节预算不能混用

| 参数 | 含义 | 当前/目标约束 |
| --- | --- | --- |
| `buffer.size` / `buffer.out_size` | ESP-MQTT 收发工作缓冲 | 当前各 512 B，不是应用消息最大长度 |
| `maxPayloadBytes` / `kMaxMessage` | 单条完整应用消息上限 | 1024 B，包含 JSON 信封、数据和字段转义后的 UTF-8 字节 |
| 状态发送预算 | 状态等低优先级消息的 outbox 使用门槛 | 1024 B，当前检查还包含 Topic 和协议余量 |
| outbox 总预算 | 未完成发送/确认消息的累计约束 | 2048 B，由应用检查及 SDK 硬上限共同限制 |

563 B 状态超过 512 B 工作缓冲，并不能证明 SDK 自动把缓冲扩容。ESP-MQTT 支持大于内部缓冲的消息传输与分片；`enqueue` 先保存消息，由 MQTT 任务发送。具体行为以项目锁定版本及字节边界实测为准，不能因为单条负载小于 1024 B 就认定一定能进入状态发送预算。[ESP-IDF 5.5 MQTT 官方说明](https://docs.espressif.com/projects/esp-idf/en/release-v5.5/esp32/api-reference/protocols/mqtt.html)

保持当前缓冲配置的前提是验证 511/512/513 B 及协议上限附近消息的发送、入站分片重组、QoS 1 确认和队列峰值；不能为凑整直接增大常驻缓冲。生产发送前使用真实编码长度和 Topic 长度计算预算。

## 6. MQTT Topic 与连接规则

| Topic 后缀 | 方向 | Retain | 用途 |
| --- | --- | --- | --- |
| `command` | NAS → 设备 | 否 | 两阶段控制 |
| `ack` | 设备 → NAS | 否 | 控制回执 |
| `state` | 设备 → NAS | 是 | 最后状态快照，收到时不一定新鲜 |
| `availability` | 设备 → NAS | 是 | 连接/断开提示，含遗嘱 |
| `capabilities` | 设备 → NAS | 是 | 能力声明 |
| `query` | NAS → 设备 | 否 | 认证、快照、设置、请求结果和统计分页查询 |
| `reply` | 设备 → NAS | 否 | 只读查询响应 |
| `time-request` | 设备 → NAS | 否 | nonce 关联的 UTC 时间请求 |
| `time-reply` | NAS → 设备 | 否 | 受 Topic 权限保护的时间响应 |

完整 Topic 沿用 `mimivent/v1/{deviceId}/{suffix}`。新增 Topic 需要同时更新 Broker ACL、Gateway 订阅和设备订阅。

- 现有命令和状态使用 QoS 1，应用层仍必须处理重复消息。
- 保持无离线控制积压的会话策略；命令不能 retain，也不能在恢复后自动补发。
- 同一设备只维护一个本地 Broker 客户端，重连由明确的生命周期管理。
- 连接成功与命令订阅成功分别记录；未完成订阅不能报告“可以控制”。
- 重连采用退避并带抖动；稳定连接后再恢复正常退避起点。
- ACK、查询响应与状态共用总硬上限，但 ACK 优先；历史查询不得挤满回执空间。
- 暂不增加独立的高频事件广播 Topic，历史事件走持久化分页查询。

## 7. 状态采样、上报与新鲜度

### 7.1 状态信封

```json
{
  "schemaVersion": 1,
  "deviceId": "32位设备ID",
  "bootId": "每次启动重新生成的随机标识",
  "seq": 123,
  "sampledUptimeMs": 456789,
  "state": {
    "fanOn": false,
    "mode": "auto",
    "phase": "armed"
  }
}
```

state 内的具体业务字段依据现有 ControlApi 输出统一映射，文档示例不代表仅保留这三个字段。编码后完整消息必须满足公布的字节上限。

- `bootId` 不作时间大小比较，不能拿随机 ID 判断哪个启动更新。
- `seq` 采用无符号 32 位整数，JSON 精确传输范围为 0–4,294,967,295；设备启动时从 0 开始。只在业务状态变化时递增，心跳不增加。
- 比较使用 RFC 1982 风格的模 2^32 序号算术：令 `d=(incoming-current) mod 2^32`，仅 `0<d<2^31` 判定为更新，d=0 为同一状态；d≥2^31 不能当更新。App/NAS 使用足够宽的整数计算差值，不能用有符号 32 位直接相减。
- 断线、NAS 重启或无法确定同 bootId 的顺序时先做关联 queryId 的新快照确认，重建基线，再接受实时消息；协议不承诺离线超过半个序号空间后仍能只靠比较恢复。增加强制回绕和半范围歧义测试，不等待真实运行到边界。
- `uint32_t` 在 1 Hz 下约 136 年回绕，约 49.7 天回绕的是 32 位毫秒计数。`sampledUptimeMs` 改用设备 64 位单调计时转换的毫秒，JSON 上限为 2^53−1；旧 32 位 uptime 不用于跨回绕排序。bootId 只在真实启动时变化，不为序号回绕伪造设备重启。
- 心跳重新采样但没有状态变化时，seq 可保持不变；`sampledUptimeMs` 更新。
- NAS 收到同 bootId、同 seq 的新心跳可刷新采样时间，但不能触发业务变化提示。
- 不依赖设备墙上时间计算存活；设备未校时不影响控制有效期和基本新鲜度。

### 7.2 上报策略

初始参数：状态合并窗口 300 ms、状态心跳 5 s、fresh 阈值 15 s、stale 阈值 60 s。它们是待实测调优的配置，不是既有性能承诺。调参满足 `freshThreshold >= 3 × heartbeatInterval`，网络延迟预算另加；这只减少闪黄，不能保证任意丢包和延迟都不进入 delayed。

1. 风机开关、模式、配置或阶段变化时标记状态待上报。
2. 风机输出和控制结果相关状态优先发布；普通连续变化在合并窗口内只发布最终状态。
3. 无变化时按心跳重新采样并发布。
4. MQTT 重连就绪后立即生成并发布完整快照。
5. 上报失败保留最新待发送状态，按预算重试，不累计无界旧快照。
6. 统计事件在业务变化时独立完整记录，不能因为状态合并而丢失。

当前每两秒周期发布的实现必须完成上述改造后，才能称为“变化主动上报”。

### 7.3 Retained 消息与启动识别

- NAS 首次收到 retained state 时标记为 `cached_unconfirmed`，不能把接收时间当作设备刚采样的时间。
- 等待新的非 retained 采样，或发起带唯一查询 ID 的只读快照请求，以确认当前 bootId 和状态。
- 不同 bootId 的切换要由新连接及新采样/查询确认，不能单凭一条 retained 数据覆盖当前状态。
- `availability=online` 只说明最后已知连接情况，不能单独证明业务状态新鲜或命令订阅就绪。
- NAS 重启后执行同样的重新确认流程，不把数据库里的旧状态直接标成在线。

### 7.4 新鲜度规则

NAS 分开保存：最后任意消息时间、最后可信采样时间、最后连接提示、最近查询结果。服务运行期间使用单调时钟计算年龄；墙上时间只供展示和归档。

| 状态 | 初始判定 | App 展示 |
| --- | --- | --- |
| fresh | 可信采样年龄 < 15 s | 在线，显示当前状态 |
| delayed | 15 s ≤ 年龄 < 60 s | 状态延迟，显示最后更新时间 |
| stale | 年龄 ≥ 60 s，或只有未确认缓存 | 设备状态未知/过期，显示最后状态 |
| device_offline | 已收到可信离线提示 | 设备离线，仍可查看标明时间的旧状态 |
| gateway_unreachable | App 无法访问 NAS | NAS 不可达，提示可用的蓝牙入口 |

阈值由 Gateway 统一配置，不能由 App 和 NAS 分别硬编码两套。响应带 `ageMs`、`freshness` 和时间信息，App 在本地继续增加年龄；App 不因 HTTPS 请求成功而重置设备采样年龄。

状态过期本身不等于控制权限失效；若设备可完成新的 prepare，仍可尝试控制。NAS/Broker/设备明确不可用时不给用户伪成功。

## 8. App 前台刷新与首页改造

### 8.1 本轮采用轮询

App 前台每两秒读取 NAS 的最新缓存，进入前台、切换设备、网络恢复后立即刷新。轮询只读取 NAS 缓存，不让每次轮询都触发设备查询；仅授权续期、首次状态确认和缺失补取才发 MQTT 查询。

NAS 接收状态与 App 获取状态是两个独立周期。“两秒轮询”不等于端到端保证两秒：还要计入设备上报、网络、处理和请求耗时。

### 8.2 调度与连接

- 复用受固定证书指纹保护的 HttpClient；不能每次请求都创建后强制销毁。当前 `tryReadState()` 仍新建并强关客户端，属于待改代码，不代表已经满足本条。
- P3 开始前先完成客户端生命周期改造：由应用级 NAS transport 管理，按 HTTPS origin 和指纹配置代次隔离客户端；不使用一个可变回调的全局客户端跨 NAS/证书复用。配置变化时取消旧代次、销毁其连接，并丢弃旧响应；退出设备上下文后清理对应资源。
- 同一设备最多一个状态刷新在途，慢请求不叠加。
- 控制和结果查询优先于普通刷新，统计分页低于控制优先级。
- App 后台停止定时器和不必要网络工作；前台恢复先展示“正在更新”，再更新状态。
- 失败按 2/4/8/最多 30 s 等初始策略退避；网络恢复可提前触发一次。
- 切设备、切通道或页面销毁后，旧响应不得覆盖新页面状态。
- 证书配置变化必须销毁旧客户端；旧证书验证不能被连接池绕过。
- 控制请求不能因轮询重试机制而自动重发。

### 8.3 首页通道选择

用户偏好与当前实际通道分别保存。首页显示 NAS 控制、蓝牙控制、连接中或不可达；实验页中的日常控制迁入统一控制入口。

| 场景 | 行为 |
| --- | --- |
| 选择 NAS 且服务可用 | 通过 NAS 控制，显示状态年龄 |
| NAS 可达但设备状态过期 | 提示过期，不把旧状态显示为实时 |
| NAS 不可达 | 保留旧状态及时间，提示连接或切换蓝牙 |
| 蓝牙已连接且选择蓝牙 | 使用蓝牙，不受 NAS 可达性影响 |
| 有待确认控制 | 先处理原请求结果，不能用切通道绕过去重保护 |

初版不承诺后台自动连接蓝牙。自动切换仅能在原请求明确未发送，或结果明确后执行；不得把“NAS 超时”当作“设备没有执行”。

## 9. 控制一致性及结果确认

### 9.1 保留现有控制协议

App 生成 UUID requestId 并在发送前持久保存。Gateway 保留当前 version 1 HTTPS 请求格式，将其转换为 MQTT version 2 prepare/execute。设备校验绑定、正文摘要、租约、有效期和安全规则，持久记录后执行。

沿用设备计时签发的短期 challenge；本轮不自行延长现有约一秒的设备执行凭据有效期，也不改成依赖 NTP 的墙上时间。Gateway ACK 总等待时间与现有 2500–3000 ms 窗口保持一致，App 总超时必须给正常链路留出余量。

### 9.2 结果状态

| 结果 | 含义 | 后续行为 |
| --- | --- | --- |
| not_sent | 明确未发布执行命令 | 可提示用户重新操作或选择蓝牙 |
| pending | 已发送，结果尚未确认 | 仅查询原 requestId |
| applied | 设备确认业务执行成功 | 保留成功，独立刷新最新状态 |
| rejected | 设备明确拒绝 | 显示设备错误码，不误报为网络失败 |
| unknown | 无法确认是否执行 | 保留原请求，查询或由用户核对后明确结束确认 |

HTTP 200 可能承载设备拒绝结果；App 必须检查业务结果。请求发送超时或连接断开通常属于 unknown，不能据此自动生成新 ID 重发。

### 9.3 持久去重

- 保留 32 条、至少 10 分钟的保护窗口；窗口内满表拒绝新请求，不覆盖受保护记录。
- 相同绑定、请求 ID、路径和正文才视为同一操作；内容冲突明确拒绝。
- 去重记录在重启后恢复，不能因为 bootId 改变就清除 App 待确认记录。持久格式不恢复上一启动周期的 `WriteRecord.at`；所有有效恢复记录统一设为当前启动的 monotonic now，至少 10 分钟保护窗口从恢复时刻重新起算。现有 `loadWrites()` 的 `w.at=now` 必须保留。
- 运行期到期判断使用有明确位宽的单调差值，覆盖 millis 回绕边界；不能用 UTC 或上一启动周期的 uptime 相减。恢复后重复请求查询返回原结果/保守未知，不再次执行；这不意味着必须把已执行的同正文重试一律报错。
- 去重不是无限期承诺。超过保护窗口或结果缺失时，原请求只查询、不自动重放。
- 保存失败不执行控制；执行成功但结果保存或 ACK 失败时保持“可能执行”，后续查询恢复。
- Gateway 重启丢失内存结果时，通过认证只读查询设备原结果，不把缓存缺失认作未执行。
- 对旧版无正文摘要记录沿用保守处理，不推断当前正文已执行。

`pendingRequestAgeMs` 只用于展示和诊断，不作为自动解锁或重发条件。App 中“结束确认”必须提示旧操作可能已经执行，并要求用户核对；不自动定时清除。

App 主控制页与 NAS 管理页必须共用同一待确认 key：`wifi.pendingControl.{deviceId}.{tokenId}`。从旧版 `mimivent.nas.pending.{deviceId}.{tokenId}` 迁移时保留原 requestId；两个 key 同时存在但值冲突时禁止发送，只有用户核对后显式结束确认才可同时清除。网关查询的网络失败、HTTP 错误与设备明确返回 `unknown` 必须分别展示：查询失败时保留原记录并说明本次新控制未发送；不能把查询失败报告为设备结果未知。首页和 NAS 管理页展示 pending 年龄，旧记录没有创建时间时显示“等待时长未知”。

### 9.4 多手机与跨通道并发

不同手机生成的不同 requestId 是不同操作，去重不等于业务合并；但当前设备已有命令锁和跨客户端控制租约，不能认定不同请求必然同时执行。沿用现有租约规则：其他持有者未释放且未超时时，拒绝抢占，不新增另一套互相冲突的 Gateway 所有权。

Gateway 对同一设备最多一个写控制处于 prepare/execute/结果等待阶段；相同请求加入原等待，不同请求立即返回明确的忙错误，声明新请求尚未发布。首版不排队自动执行按钮操作，避免用户等待后突然排风。将来增加队列时必须有容量、到期、取消和入队时刻语义，排队完成后才签发短期 challenge。

设备业务锁和租约仍是最终裁决者，覆盖蓝牙与 NAS 并发；Gateway 的进程内限制不能防止蓝牙或另一个 Gateway。一个请求结果未知后，不自动释放设备端保护；Gateway 后续请求仍须遵守 §9.2 和设备裁决。测试两台手机、两种相反操作、同手机连点、BLE 与 NAS 同时控制、Gateway 重启及租约到期边界。

## 10. MQTT 只读查询与设置

移除设备 HTTPS 后，快照、设置、历史分页、权限验证和旧请求结果查询都需要明确的 MQTT 只读协议，不能只完成写控制。

### 10.1 查询约定

- query/reply 使用 `schemaVersion: 1` 和唯一 `queryId`，关联 deviceId、tokenId 和本次查询类型。
- 设备核验现有绑定 bearer token；token 仅在必要消息中出现，不进入状态、诊断、持久历史或日志。
- query 不 retain、不产生风机动作、不获取或延长控制租约。
- 查询超时不自动转换为写命令。Gateway 过滤不属于本次等待窗口、设备和查询 ID 的响应。
- 同设备只允许有界并发：首版最多一个统计分页查询和一个高优先级只读请求在途。
- 完整编码消息不超过 1024 B；接收分片必须校验长度、偏移和超时。统计按字节预算分页，不依赖固定条数一定放得下。
- 只读请求在退避和队列预算中占用有界资源，不能阻塞 ACK 或本地状态机。

首版查询类型：`auth.validate`、`state.snapshot`、`settings.get`、`control.result`、`statistics.manifest`、`statistics.page`、`events.page`、`diagnostics.get`。各类字段、错误码和大小边界在实现前补充到协议文件并与 fixture 一起版本化。

### 10.2 设置写入

设置读取和写入不能混为只读查询。设置写入必须有请求 ID、参数校验、去重、明确 ACK 和写后版本确认。根据现有 ControlApi 能力单独增加受控写操作；未经 Gateway 与固件同时声明支持，不把设置页面开放成可保存。

## 11. 认证、绑定撤销与部署边界

### 11.1 App 到 NAS

- 所有 API 均校验设备对应权限：控制及设备查询使用原始绑定 bearer，NAS 缓存/历史只读可使用 §11.2 的独立 read grant；不把只读权限扩大到设置、控制或诊断查询。
- tokenId 和 deviceId 是索引，不是凭据；给响应补 `bindingState: active` 不能代替真实验证。
- 控制始终由设备再次校验绑定；NAS 缓存授权不能绕过固件授权。
- App 验证 NAS HTTPS 固定指纹，指纹错误明确报错，不静默标成“设备离线”或关闭验证。

### 11.2 将设备实时授权与 NAS 归档读取授权分开

30 s 的设备授权缓存不应成为离线归档读取的唯一凭据；但“状态标 stale”不是授权，不能无条件放行过期 bearer。

首版增加独立、仅用于该设备缓存/归档的 NAS 读取凭据（read grant）：

1. 首次登记必须在设备在线时，经 `auth.validate` 验证真实绑定，并绑定 Gateway 身份、deviceId 和 tokenId。Gateway 产生至少 256 位随机读取凭据，经已校验的 HTTPS 交给 App；App 安全保存，NAS 数据库只存凭据摘要、权限范围、到期和撤销状态。
2. read grant 有效期默认 7 天；设备在线时最多每 30 s 合并进行一次原始绑定验证，验证成功才允许续期。原始设备 bearer 不持久保存到 NAS；没有携带原始 bearer 的请求只使用已签发读取权限，不自动续期。
3. 使用 read grant 的请求只允许读取该设备状态缓存与已归档历史，不允许控制、设备查询、配置写入、OTA、授权管理或任意设备 ID。无凭据、失效凭据、凭据与设备不匹配时拒绝；不能因设备离线降级为匿名访问。
4. 设备离线时，只要 read grant 在 NAS 上仍有效，允许读取已有缓存和归档；状态强制报告离线或 stale、`lastSampledAt`/`ageMs`，历史带 coverage。无可信绝对采样时间时返回 null 并给出最后接收时间及来源，不能伪造采样时间。离线不会把凭据自动延长到永久。
5. NAS 重启从数据库恢复 read grant；时钟倒退或到期时间无法可信判断时拒绝续期并要求重新验证，不重置有效期。NAS 的时间同步和持久化均属于此功能部署前提。
6. NAS 本地授权管理可立即撤销 read grant；管理入口使用受保护的 NAS 管理员/维护权限，read grant 本身没有管理权限。设备撤销绑定的明确响应或已验证绑定变更消息也会撤销关联 read grant。
7. 若设备离线期间只在设备端撤销绑定，NAS 无法立即知道；旧读取凭据可能持续到 NAS 获知撤销或最长 7 天到期。这是离线读取能力的明确权限边界，不承诺即时失效。写控制始终由设备实时验证，不受该读取宽限影响。要求立即停止离线读取时，应同时在 NAS 撤销权限。
8. read grant 过期且设备不可达时不开放 NAS 数据；App 可以显示已授权保存的本机缓存。更长离线授权需要显式调整策略，不在客户端隐藏延长。

App 通过专用读取凭据头提交 read grant，与控制使用的原始 bearer 分离；具体头名及签发/撤销端点在 P0 固化为协议 fixture。尚未实现 read grant 的旧版保持原本保守策略，不能仅修改前端 stale 标签就开放归档。

### 11.3 MQTT 权限

设备账号只订阅自己的 command/query/time-reply，发布自己的 ack/reply/state/availability/capabilities/time-request。Gateway 账号按管理设备范围发布和订阅。现有共享宽权限账号是现场基线，不代表已达到目标 ACL；先测试独立账号及 ACL，再轮换，不能直接破坏现有设备配置。

本阶段 1883 仅位于受控局域网，不配置公网转发。未来云端必须另行引入 MQTT TLS、设备独立凭据和权限隔离，不能把现有 NAS 密码原样用于公网。

## 12. 历史统计、事件及 NAS 归档

### 12.1 权威关系

设备负责原始事件和有限历史；NAS 保存长期归档。设备数据自然淘汰不删除 NAS 历史。用户主动清空、修正时区或统计口径变化属于显式数据变更，需要独立批次或修订流程，不能根据“查询没返回”推断删除。

### 12.2 增量同步标识

历史协议至少提供：

- `dataEpoch`：统计数据批次，不等于 bootId；正常重启不换批次。
- `eventSeq`：批次内稳定、可排序的事件序号；重启不能导致重复使用已归档序号。
- `eventFirstAvailableSeq` / `eventLastAvailableSeq`：设备当前保留的范围。
- `dayKey`、`timezoneVersion`、`revision`：日汇总身份和修订版本。
- `cursor`、`hasMore`、本页边界：支持断点续传和幂等写入。

序号的持久化应与现有统计快照一起完成，避免每个事件单独写 NVS。App 与 Gateway 不根据接收先后给原始事件临时编号。

统计时间语义沿用[统计设计 §8.4](statistics-query-storage-v2.1.md#84-偏移变更策略本版新增d7)：`tzOffsetSeconds` 按设备统计批次永久冻结，连同 `tzVersion`/协议中的 `timezoneVersion` 原样归档。NAS 不得用自己的时区、手机当前时区或夏令时规则重算 dayKey 和日边界；UTC 校时不改变该偏移。字段命名映射在 P0 明确，不能并存两个含义不同的时区版本。

### 12.2.1 分页预算及耗时

1024 B 是完整 query/reply JSON 的字节上限，不是 events 数组单独可用空间。按评审提供的约 160 B/事件估算，6 条已占 960 B，通常放不下 queryId、版本、游标和完整性字段，不能直接定为每页 6 条。

首版以每页最多 4 条事件为初始上限，实际编码时再按字节预算缩小；预留约 256 B 信封时，4 × 160 + 256 ≈ 896 B。必须以字段最坏值、转义和 UTF-8 实测，超限则缩页；单条合法记录也放不下时返回明确的协议大小错误，不能无限重试或截断 JSON。

估算三天 60 条事件至少 15 页，256 条至少 64 页。总耗时约为页数 × 单页往返时间，再加调度、授权及重试；若单页 150 ms，理想下限分别约 2.25 s 和 9.6 s，并非已实测承诺。NAS 后台归档与 App 打开页面解耦，界面优先展示已有缓存并报告同步进度，不等待全量补齐。

P4 验收记录每页字节、条数、单页 P95、60/256 条完整同步时间及控制响应。统计同步可降速或暂停以让出控制；预算变更不得通过放宽无界消息来掩盖。日汇总同样按真实编码字节分页。

### 12.3 NAS 存储

首版采用 SQLite，数据目录挂载持久卷；具体 Node 驱动实现时按当前运行环境评估并锁定版本。

建议逻辑表：设备及批次、事件、日汇总、同步游标、覆盖区间和缺口。事件以 `(deviceId, dataEpoch, eventSeq)` 唯一；日汇总以设备、批次、日期及口径唯一，并按 revision 更新。

一页数据与对应游标在同一事务提交；提交失败不得推进游标。未完成的当天汇总允许修订，不能首次同步后永久冻结。

设备重连时先获取 manifest，再补缺失范围。设备已淘汰的缺口记为无法补齐，不用 0 填充；不反向把 NAS 全量历史写回 ESP32。

### 12.4 覆盖范围

```json
{
  "source": "nas_archive",
  "dataEpoch": "统计批次",
  "coverage": {
    "daily": {
      "from": "2026-11-01",
      "to": "2026-11-07",
      "complete": true,
      "gaps": []
    },
    "events": {
      "from": "2026-11-04T00:00:00+08:00",
      "to": "2026-11-07T00:00:00+08:00",
      "complete": false,
      "gaps": [{
        "from": "2026-11-05T00:00:00+08:00",
        "to": "2026-11-05T01:00:00+08:00",
        "reason": "device_history_evicted"
      }]
    }
  }
}
```

complete 按本次查询要求的整个区间判断，不是仅按实际返回的最早/最晚记录判断；端点无记录也可能是有效的零事件区间。日汇总与事件分别报告完整性，并区分来源：设备、NAS 归档、本机缓存。时间区间统一约定为左闭右开；daily 的日期范围单独约定为包含起止日期。

## 13. 存储和内存预算

### 13.1 ESP32 闪存

沿用现有分区表，不整片擦除、不自动格式化已初始化的 statistics 分区。

| 区域/内容 | 预算或上限 | 约束 |
| --- | --- | --- |
| NVS | 当前 20 KiB | 保留 WiFi、绑定、MQTT、身份及必要 OTA 元数据；考虑 GC 空页 |
| statistics 分区 | 当前 512 KiB | SPIFFS 可用容量不能等同分区原始字节数 |
| 当前统计快照双槽 | 保守按 2 × 14,536 B | 实际长度随数据量变化，格式变更重新测量 |
| 去重双槽 | 2 × 2,696 B | 独立文件名，校验后执行控制 |
| 升级遗留统计文件 | 按现场清单计入 | 未确认用途前不能自动删除 |
| SPIFFS 索引、页和 GC 余量 | 实测确定 | 不能按“每文件 4 B”估算 |

实施时补一份文件白名单及实测占用清单。以最坏数据量、迁移期间旧新文件并存、去重写入重试来测试可用空间，不只测空设备。

所有新增持久化必须声明：分区、文件名/键名、最大大小、写入频率、迁移和回滚行为。空间不足时停止相关写操作并报告，不自动删除统计、绑定或 OTA 任务。

### 13.1.1 旧 NVS 去重键清理

当前实现已在新文件写入并读回校验后调用 `nvs_erase_key` 删除 `mv-p4req/req-a`、`mv-p4req/req-b`，不是旧 blob 永远不删；但返回值和提交结果还需要完善处理。

目标清理规则：只在有效文件槽确认后清理这两个白名单键；未找到视为已经清理，其他错误记录具体错误码，检查 commit 后才报告完成。清理失败保留旧键并在后续安全时机重试，不影响已经校验成功的文件控制记录；不能清空整个 namespace/NVS。

逻辑删除并不等于立即擦除物理页；由 NVS GC 回收，不能承诺 free entries 即刻增长固定值。迁移断电时必须至少有一份有效记录，回滚约束见 §18。配额表同时统计迁移期 NVS 旧键与 SPIFFS 新文件并存。

统计快照容量和去重事故依据分别见[统计设计附录 D.6](statistics-query-storage-v2.1.md#d6-事件容量变更同样属于落盘布局变更)、[附录 D.7](statistics-query-storage-v2.1.md#d7-控制去重记录不能放-nvs)。数字变更时同步更新两份文档；不得把“剩余原始字节”直接等同 NVS 可写容量。

### 13.2 运行时资源

- 记录空闲内部堆、最大连续块、最低余量、任务栈余量、outbox 和查询在途数量。
- 状态 JSON、历史分页、队列和 pending Map 都有硬上限，不按网络输入无限增长。
- 优先减少重复 JSON 构造、重复轮询、常驻缓冲和重复客户端；不凭平均堆余量断定不存在碎片问题。
- BLE、MQTT、统计读写并行压力下，本地业务时限仍需满足现有行为契约。

## 14. 蓝牙职责和同步优化

保留：WiFi 配网、Broker 配置、设备绑定/撤销、诊断、备用控制、签名 OTA。

统一请求调度的优先级：控制与结果查询 > 状态/配置 > 统计分页。OTA 为独立受控模式，不能用普通队列优先级破坏现有 OTA 独占和恢复流程。

- 高优先级只能在安全的请求/分页边界插入，不混淆现有分片响应。
- 统计限制单页编码字节数，支持取消和游标续传。
- 已排队但未发送的低优先级刷新允许合并或取消。
- NAS 正常时蓝牙不重复高频读取同一份状态；诊断与维护请求仍可显式发起。
- 不通过盲目增大发送频率、MTU 或缓冲来承诺提速。
- 以统计同步期间的控制响应时间、失败率和本地业务时限作为验收指标。

### 14.1 OTA 期间的 MQTT 可见性

当前代码在 OTA 活跃时销毁 MQTT 客户端；这不只是停止发布。目标行为是在可行时先发布结构化 availability，携带 `reason: ota` 和有限维护期限，再主动断开 MQTT，给 BLE OTA 留出资源。正常主动断开不保证触发 Broker 遗嘱，因此不能只依赖 LWT。

Gateway 缓存最后维护原因及到期时间，App 显示“固件升级中，网络状态暂不可用”，禁用普通远程写控制。维护标记不能使旧风机状态变成 fresh。通知是尽力而为：网络已断、内存不足或发布失败时按离线/未知显示，不能阻塞 OTA，也不能谎称 NAS 一定收到通知。

维护标记建议有效 5 分钟，到期而未恢复时显示“升级后尚未重新连接”，不永久显示升级中。新的可信启动/采样清除标记；OTA 放弃、失败或完成后都要恢复 MQTT 并发送能力和完整快照。App 的 BLE OTA 页面可依据直接回执显示更准确进度，不凭 Gateway 的维护缓存推断安装成功。

结构化 availability 使用独立 schemaVersion，并兼容旧 online/offline 字符串；升级 Gateway 前不能直接改变旧部署所期望的格式。

### 14.2 蓝牙连接及 WiFi 恢复后的校时

蓝牙和 WiFi/NAS 两条链路均应在就绪后触发 UTC 校时，校准与配网成功、MQTT 认证成功是独立结果：

| 触发条件 | 时间来源与传输 | 规则 |
| --- | --- | --- |
| 蓝牙已连接并完成配对/授权 | App 当前 UTC，经已授权 BLE 校时接口 | 首次就绪及每次有效重连各触发一次；短时间重复连接合并。失败时在本次 BLE 会话内按有界退避重试，断开后取消旧请求；不等待统计全量同步 |
| WiFi 已获得 IP，且 NAS MQTT 连接与必需订阅均就绪 | NAS 系统 UTC，通过受保护的 MQTT 校时交换 | IP 到达只标记待校时；Broker、订阅或时间健康源未就绪时按有界退避重试，不把联网状态当校时成功 |
| MQTT 重连、设备时间无效或校时失败恢复 | 同上 | 每个新 MQTT 会话使用新 nonce 重新取时；拒绝旧 nonce 和 retained 时间消息。重试有上限/退避，不阻塞风机控制 |

BLE 与 WiFi/NAS 是两条独立触发链路，不能以其中一条成功代替另一条的实现或验收。BLE 授权初始化负责首次冻结统计时区，并可提供手机 UTC；冻结偏移后，已就绪的 MQTT 会话必须立即重新请求 NAS UTC。之后 BLE 和 WiFi/NAS 各自有效重连时仍按来源优先级处理校时；NAS 不可达时手机可作备用，不能因 NAS 校时待处理而阻塞 BLE 控制或设备本地功能。

本阶段采用 NAS 作为联网时间来源，不要求 ESP32 直连公网 NTP。NAS 自身必须通过以下时间健康门槛；App/NAS 不具备可靠时间时，显示校时未完成并允许基本本地控制继续运行，不把无效日期写入正常历史。

#### 14.2.1 NAS 时间健康及来源优先级

NAS 主机侧配置时间健康提供器，读取实际使用的系统同步服务状态（例如 systemd-timesyncd 或 chrony，由部署现场确定），给 Gateway 只读健康信息；容器内 Date.now() 正常、能联网或 NAS 开机很久都不是健康证据。不要求为 Node 容器开放宿主机管理权限。

初始门槛同时满足：本次主机启动后至少一次同步成功、服务报告已同步、距最近成功同步不超过 6 小时、已报告的时间偏差绝对值不超过 1 s。主机休眠恢复或检测到时钟跳变后，重新同步前撤销健康。健康提供器每 10 s 刷新递增序号，Gateway 通过本地单调时间观察序号超过 30 s 未推进即判定未知，避免用可能错误的墙上时间检验自身。

健康源不存在、字段未知、服务不同尚未适配或超出任一门槛时，`time-reply` 返回 `accuracy: unavailable` 和原因，不附可采纳的时间。成功响应给出 UTC、实际误差估计（若来源能提供）和同步年龄；不能把“偏差 <1 s”伪称为端到端绝对精度证明。P0 固定该 schema 和部署适配器，未适配时不得默认健康。

时间来源顺序：健康 NAS > 已授权且时间有效的手机 > 保留现有设备映射/未校时。最近 60 s 内有可信 NAS 样本时，手机校时只核对、不覆盖；NAS 不可达、健康未知或样本过期后，才允许手机作为备用来源。手机来源的系统自动时间状态/质量未知时要报告“时间已按手机时钟校准，准确度未验证”，不能仅因蓝牙已配对或 BLE 校时 ACK 成功就声明绝对时间正确；设备当前时间有效性与时间源准确度应分别表达。

UTC 校准来源与统计时区初始化是两个独立状态。BLE/授权初始化流程负责首次写入并冻结设备统计偏移；NAS 的 `time-reply` 只提供 UTC 与时间质量，不得以 NAS 主机的 `utcOffsetMinutes` 初始化或覆盖设备偏移。设备尚未初始化冻结偏移时，WiFi/NAS 校时记为待处理，不采纳会隐式建立统计时区的回复；偏移经 BLE/授权流程固定后，按当前 MQTT 会话重新请求 NAS UTC 并重试。已有偏移时，NAS 校时始终沿用设备偏移，NAS 本地时区变化不改变统计日界线。

NAS 恢复时按同样的二次采样、冲突与活动安全边界处理，不能为落实“NAS 优先”立即跳时。NAS/手机差 30 s 等明显冲突继续执行下述保留现值、报告冲突规则；优先级决定候选源，不豁免质量验证。

MQTT 时间同步是独立的受控操作，不混入风机 query：设备产生随机 nonce 和本次请求的单调起点，NAS 仅对当前设备的请求返回 UTC 毫秒、nonce 和来源质量；设备验证专用 Topic 权限、关联 nonce 和限定往返时间。响应不 retain，初始超时上限 2 s，超时作废并重新取时，不能重放旧报文。P0 明确增加 `time-request`（设备发布）/`time-reply`（Gateway 发布）及 ACL，仅 Gateway 可回复；共享宽权限账号未整改前不能宣称该时间来源受到设备级隔离保护。

蓝牙校时同样要求授权、关联请求和有限往返时间。可用单调往返估算传输误差；超过 2 s 不采纳。手机和 NAS 近同时校时时串行处理，记录 UTC、源、误差估计和最后校准 uptime；偏差在小范围内的重复请求可返回“已准确，无需调整”，避免反复跳时及写存储。

已校准后出现超过 5 s 的修正先再次采样确认；来自不同来源且仍明显冲突时保留现值、报告时间冲突，由用户检查 NAS/手机系统时间，不靠最后到达者随意覆盖。阈值是初始策略，需在 P0 和 fixture 固化。

校时只调整 UTC 与单调计时的映射，不修改冻结的 `tzOffsetSeconds`，不重置 bootId/seq，不影响风机倒计时、PIR 间隔、challenge 有效期、租约和去重窗口。冷启动未校时的基础回填遵循[统计设计](statistics-query-storage-v2.1.md)，后续跳变必须另外满足 §14.2.2，不能用引用替代具体规则。

#### 14.2.2 首次校时、活动进行中及后续跳变

实现状态（2026-11-07）：`StatisticsStore.cpp` 已将活动合并间隔、活动跨度和日桶增量改为当前启动内的单调毫秒差值；UTC 作为活动起点的日历锚点，仅用于把累计跨度映射到日桶。检测到墙上时间回拨时保留活动追加顺序并设置 `clockWentBackwards`。原生回归用例覆盖活动中 UTC 回拨 300 秒而单调活动时长仍增加 30 秒。设备 OTA 后的真机验证仍需单独完成。

1. **首次可信校时**：无有效 UTC 的当前启动记录保持 unsynced，时长仍按单调计时累计。建立可信映射后，用同一份映射统一回填本次启动内仍可确定的事件及在途活动起点；不能混用两套映射给同一活动的开始和结束打时间。无法证明属于当前启动的旧记录不按当前 uptime 回填。
2. **已有 UTC、活动尚未结束**：活动段、PIR 离开确认、排风及待消费的入厕活动样本还在进行时，暂不步进 UTC 映射；记录待重新校时，继续沿用旧映射和冻结偏移。到达这些业务都已结束的安全边界后重新取时、重新验证，不能直接套用等候数分钟的旧 UTC 响应。连接后可立即报告“校时待安全边界”，不把它报告为已完成。
3. **后续有效校正**：在安全边界一次性应用；此前已定稿事件保留时间戳和归属，此后新活动使用新映射。不设置任意的 60 s 分界，不把原来可信的记录批量重标为 timeUnsynced（旧标志还承担 uptime 编码语义）。超过 5 s 的候选仍需二次采样与冲突处理，见上文。
4. **跨午夜与回拨**：真实活动若跨日，活动跨度/运行量仍按既有统计口径分摊，入厕样本保持其活动起点日；不会因校时强行拆分为两个活动。时间回拨后 UTC 非单调是允许且须诊断的现象；事件按统计设计 §6.7 设置 `flags.bit2=clockWentBackwards`，保留追加顺序和原始时间，不排序、不丢弃。事件顺序以 `dataEpoch/eventSeq` 为准，NAS 不按时间戳去重或擅自改写 dayKey。此情况不等同于 `timeUnsynced`，不得覆盖其既有编码语义。
5. **归档与质量**：首次回填造成日汇总修订时增加 revision，并让 NAS 通过增量修订取得相同结果；不能只增 eventSeq 导致此前归档的临时数据永远不更新。记录校正前后偏差、应用单调时刻、来源和影响批次；更细时间质量元数据需独立定义格式，不能占用现有 flags 随意改义。

以上是目标约束而非已实现保证。活动长期不进入安全边界时展示待校时，不为了 UI 显示“成功”强行改时；如后续需要无跳变平滑校时，单独设计并验证，不在本轮隐式引入。

尚未初始化统计批次时，首次冻结时区偏移按原有授权初始化规则执行；之后手机或 NAS 更换时区不能隐式改动设备偏移。需要更换统计偏移时走既有显式重置/新批次流程，不借连接校时悄悄修改。

状态只暴露精简的 `timeSynced` 和时间来源标识；详细 lastTimeSync、偏差、错误和重试次数按需诊断。校时成功必须有设备回执，联网或蓝牙连接成功不能代替校时成功。

## 15. NAS 运维与可观测性

开工前备份 NAS 实际源码、compose、证书和配置；凭据备份不进入 Git。将现场 state 订阅、`/state`、认证及请求日志等改动与工作区逐项比对，通过检查后形成可重建镜像的版本基线。

不要把 `/tmp` 或正在运行的容器当作唯一源码。部署记录包含源码提交/摘要、镜像摘要、配置版本、部署时间和回滚镜像。数据库和配置使用持久卷。

### 15.1 Gateway 持久卷部署门槛

当前工作区 compose 的 Gateway 只有 TLS 挂载，没有数据库目录；现场若另有 server.mjs 挂载也不能代替数据卷。P4 上线前必须增加独立持久路径，例如：

```yaml
services:
  gateway:
    environment:
      DATA_DIR: /app/data
    volumes:
      - ./data/gateway:/app/data
```

示例是合入原 compose 的增量，不能覆盖掉 TLS 等已有挂载；路径在当前部署中对应 `/vol1/1000/docker/mimivent/data/gateway`。容器数据库、read grant 注册表及 SQLite WAL/SHM 都放同一持久目录。使用实际 Gateway UID/GID 预建目录并验收权限，不能改成全局可写规避问题。

部署检查：目录可写、数据库成功迁移、磁盘满/只读时有明确错误、备份包含一致数据库及所需密钥、`up --force-recreate` 后历史/授权仍存在、从备份恢复能继续同步。SQLite 备份采用一致性备份机制，不能在 WAL 写入中只复制主 db 文件。数据库提交失败不推进统计游标，不无界占用内存，也不能把落库失败误报为控制尚未执行。

最小诊断字段：

| 层 | 字段 |
| --- | --- |
| 设备 | bootId、MQTT 连接/订阅就绪、重连原因、入队拒绝、发送失败、堆和栈、存储失败阶段 |
| NAS | Broker 连接、状态年龄、缓存来源、授权租约、在途请求、归档游标/缺口、数据库错误 |
| App | 实际通道、NAS 地址、刷新时间、错误类别、pendingRequestAge、当前请求阶段 |

日志关联 requestId/queryId、通道、阶段、耗时和结果码；不输出 bearer token、Broker 密码、完整 command 或证书私钥。诊断导出采用字段白名单。

### 15.2 诊断字段的传输路径

bootId、seq、简要时间有效性和必要维护状态进入精简 state；堆、栈、重连原因、丢弃计数和存储错误不持续塞入每条 state。详细诊断走已授权的 `diagnostics.get` → reply，并按 mqtt/memory/storage/time 等组分页，完整响应仍受 1024 B 上限约束；首版不增加常驻 diagnostics 广播。

Gateway 自身数据库、请求阶段和缓存年龄由其认证诊断 API 提供；App 的本地 pending 年龄不要求设备回传。状态类预算、诊断查询预算和 ACK 优先级分别验收，诊断采集不能改变风机行为或导致高频写闪存。

健康接口区分“进程运行”“Broker 已连接”“指定设备可用”，不能只用一个 ok 代表全部链路。历史数据库定期备份，并验收恢复流程。

| P6 稳定验收 | 故障注入、长时间运行、部署与恢复 | 无阻塞性问题，再规划云端 |

P3 与 P4 在 P0/P1 协议和调度稳定后可以分别推进，但共享协议变更需统一版本，不能各自改字段。版本/能力设计在 P0 完成，不拖到云端阶段。

P1 仅拆分源代码，不重新开启已经关闭的设备 HTTPS。若需要验证旧 HTTPS 兼容，使用独立短时测试构建，不能把它部署为过渡日常固件。P1 的 24 h 门槛允许后续发现问题再修复，但不能省略阶段验证直接宣称稳定。

## 18. 兼容、部署与回滚

- 先部署可兼容当前控制协议的新 Gateway，再升级固件，最后升级依赖新能力的 App；每步都有明确能力检查。
- 保存固件、App、Gateway 镜像及协议 fixture 的对应版本清单。
- 旧 App 尚不支持 NAS 首页时，蓝牙控制仍需可用；不能把新能力缺失表现为卡住。
- 去重存储从 NVS 迁入文件后，旧固件未必读取新文件。回滚不能只看统计 schema：必须同时检查去重格式和控制保护兼容性。
- 不允许在有未确认控制时自动回滚到不认识当前去重记录的固件。维护回滚需先停止远程写入口、核对设备实际状态，并建立明确的旧请求关闭策略。
- 不整片擦除，不为解除报错清空绑定/统计，不自动删除未知文件。
- NAS 数据库采用有版本的迁移和备份；不支持直接降级的数据格式必须阻止无备份回滚。
- App 降级不是清空状态的理由：兼容的绑定、读取授权及 pending 格式继续保留；不认识的格式必须隔离并阻止写控制，不删除后“重新开始”。旧 App 可能没有保护逻辑，因此受控发布/安装流程必须核对支持范围，在未知结果存在时不执行不兼容降级；不能承诺新版代码可以阻止用户绕过流程强制安装任意旧 APK。原始 requestId 和保护标记不能仅存在新版才认识的可选字段中。

## 19. 本轮完成判定

只有在首页可通过 NAS 控制、状态新鲜度正确、历史覆盖范围可解释、蓝牙备用和 OTA 正常、未知结果不误重发，以及断网/重启/存储边界验收通过后，才将此方案标记为完成。

后续云端和米家工作基于该稳定基线独立设计，不在本轮默认开放公网端口、增加云端凭据或改变设备本地自动控制规则。
